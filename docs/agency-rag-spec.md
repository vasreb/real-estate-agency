# Спецификация RAG-ассистента для агентства недвижимости

## 1. Назначение и границы

Ассистент отвечает на вопросы сотрудников по договорам, допсоглашениям, карточкам объектов и рыночным отчётам. Каждый существенный вывод сопровождается ссылкой на документ и страницу. Если доступных источников недостаточно или они противоречат друг другу, ответ объясняет, что именно удалось подтвердить.

RAG расширяет существующее приложение **Next.js + TypeScript и PostgreSQL**. Он использует готовые сделки, документы, учётные записи и права команд. Поиск работает через `pgvector` в той же базе. Для поиска используется облачная многоязычная модель эмбеддингов Voyage AI (архив на английском, интерфейс на русском), для ответов — Claude API. Для первой версии берётся `voyage-4` или более лёгкая `voyage-4-lite`; точная модель выбирается по результатам эталонных вопросов. Бесплатных 200M токенов хватает на индексацию архива (~3–4M токенов) с запасом на переиндексацию. Размерность вектора — 1024. Векторный индекс в первой версии не создаётся: при ~10 тысячах фрагментов точный перебор с фильтром по команде и сделке достаточно быстр и не теряет результаты из-за фильтрации. HNSW добавляется, если корпус или задержка это потребуют. Тексты документов отправляются провайдеру, для реальных договоров это требует согласия заказчика. Запасной вариант — локальная модель, схема это допускает через идентификатор модели в `document_chunks`. [Документация pgvector](https://github.com/pgvector/pgvector)

**Инфраструктура.** Во всех окружениях (локальная и тестовая БД, `compose.production.yaml`, CI) образ `postgres:18` заменяется на образ с `pgvector`. Расширение включается отдельной миграцией. Ключи Claude API и провайдера эмбеддингов задаются переменными окружения бэкенда и добавляются в `.env.example`.

## 2. Документы и область поиска

| Область     | Какие документы доступны                                                                                          |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| **Сделка**  | Договоры, допсоглашения, карточки объектов и другие файлы выбранной сделки. Доступ наследуется от команды сделки. |
| **Команда** | Документы всех доступных сделок выбранной команды и её общая коллекция, например рыночные отчёты.                 |

У документа есть один владелец доступа — сделка или команда напрямую. Существующие файлы остаются привязаны к своим сделкам. Для отчётов и других общих материалов добавляется возможность загрузки в коллекцию команды. Связь `parent_document_id` по-прежнему указывает на конкретный договор той же сделки. Документы коллекции команды не имеют `parent_document_id`, а типы `contract` и `amendment` для них недоступны.

Номер сделки уникален только внутри команды, поэтому один и тот же номер может существовать в разных командах. Поиск по номеру всегда ограничен выбранной командой.

## 3. Индексация документов

**Вход** — существующие и новые PDF и DOCX. **Результат** — поисковые фрагменты с текстом, эмбеддингом и точной привязкой к источнику.

- **PDF с текстом.** Текст извлекается постранично. Номер страницы соответствует исходному файлу.
- **PDF со сканами.** Страницы и области с изображениями текста обрабатываются OCR. В смешанном PDF сохраняются и исходный текстовый слой, и распознанный текст. Подписанный оригинал используется как источник и хранится в исходном виде. [Режимы OCRmyPDF](https://ocrmypdf.readthedocs.io/en/stable/advanced.html)
- **DOCX.** Для постраничных цитат создаётся PDF-представление. Поисковый текст извлекается из него, и цитата открывает это же представление. Оригинальный DOCX доступен для скачивания.
- **Фрагменты.** Разбиение учитывает страницы, заголовки и пункты договора. Если фрагмент охватывает несколько страниц, сохраняются обе границы диапазона.

Обработка идёт в фоне в отдельном воркере (контейнер Docker с OCRmyPDF, Tesseract и LibreOffice). Очередь — обычная таблица задач в PostgreSQL без отдельной библиотеки: воркер периодически забирает задачи запросом `SELECT ... FOR UPDATE SKIP LOCKED`, повторяет неудачные и записывает причину ошибки. API только ставит задачи и читает статусы. Добавление воркера оформляется ADR. Лимиты на размер файла и число параллельных загрузок остаются прежними (ADR-0002). Оригиналы и PDF-представления хранятся в `bytea`, как и сейчас. При подключении RAG существующие файлы ставятся на первичную индексацию. Загрузка нового файла создаёт задачу обработки. Повторная индексация заменяет активные фрагменты только после успеха. При ошибке администратор видит причину и может повторить обработку. Удаление документа удаляет его фрагменты и PDF-представление.

## 4. Данные в PostgreSQL

| Изменение             | Что хранится                                                                                                                                                                                                                                                                                                                                        |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`documents`**       | `deal_id` становится необязательным, добавляется `team_id`; `CHECK` требует ровно одного из них. Составной внешний ключ `(deal_id, parent_document_id)` сохраняется для документов сделки. Состояние обработки, дата последней успешной индексации, сообщение об ошибке и PDF-представление для DOCX. Статус подписания договора хранится отдельно. |
| **`document_chunks`** | ID фрагмента и документа, порядковый номер, диапазон страниц, пункт или раздел, текст, эмбеддинг и идентификатор модели эмбеддингов. Фрагменты удаляются каскадно вместе с документом.                                                                                                                                                              |

При обработке документов и вопросов используется одна и та же модель эмбеддингов. При её замене корпус переиндексируется, а поиск переключается на новую модель после подготовки её индекса.

## 5. Агент, поиск и цитаты

В чате работает **один агент Claude с тремя инструментами чтения**. `POST /api/chat` принимает вопрос, историю диалога, выбранную команду и, если сотрудник сузил область поиска, ID сделки. Бэкенд определяет сотрудника по сессии и проверяет выбранную область. Агент сам выбирает инструмент, использует его результат для следующего вызова, задаёт уточняющий вопрос или формирует ответ. Сервер выполняет вызовы через SDK Anthropic, проверяет аргументы и права при каждом обращении и возвращает результаты модели. За один вопрос возможны несколько вызовов, ограниченных бюджетом шагов и контекста. [Цикл вызова инструментов Claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)

| Инструмент                         | Вход и результат                                                                                                                                                                                                                                                                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `search_records(query)`            | Принимает свободный текст с номером сделки или частью адреса. Возвращает доступные совпадения по объектам и сделкам с точным адресом, номером сделки и внутренними ID для следующих вызовов.                                                                                     |
| `get_property(property_id)`        | Принимает проверяемый ID объекта из поиска или интерфейса. Возвращает адрес объекта и доступные связанные сделки с внутренними ID. В базе у объекта нет других полей, поэтому арендатор, ставка, комиссия и другие условия берутся только из договоров через `search_documents`. |
| `search_documents(query, filters)` | Принимает вопрос или поисковую формулировку и необязательные фильтры по сделке, типу или ID документа. Сочетает поиск по реквизитам и тексту с поиском по смыслу через `pgvector`. Возвращает отрывки со страницами, метаданные источников и сведения о пробелах в проверке.     |

### Контекст диалога и кеширование

API Claude не хранит состояние, поэтому с каждым вопросом сервер заново собирает и отправляет контекст. Историю диалога хранит клиент и присылает только текст прошлых вопросов и ответов (с данными цитат) и компактное состояние: ID найденных сделок и документов. Результаты инструментов от клиента не принимаются, права на ID проверяются при каждом вызове. В базе история не хранится.

Расход токенов снижается кешированием промпта: системная инструкция и описания инструментов образуют стабильный префикс, маркер кеширования ставится в конце истории. Нужно проверить минимальную длину кешируемого префикса для выбранной модели.

**Гипотеза, подлежащая проверке:** между вопросами отбрасывать результаты инструментов из прошлых ходов, оставляя только текст ответов с цитатами. Это сокращает контекст, но может ухудшить уточняющие вопросы («а что в пункте 4.2?»), если нужного отрывка уже нет в контексте. Если эталонные вопросы покажут потери качества, результаты инструментов сохраняются в истории (они всё равно читаются из кеша дешевле), либо сохраняются выборочно. Решение принимается по замерам из §7: расход токенов и качество ответа на уточнениях.

### Поиск объекта или сделки

При наличии ID из интерфейса или предыдущего результата агент может сразу обратиться к нужному инструменту. При свободном описании он передаёт в `search_records` исходные ориентиры сотрудника. Бэкенд нормализует регистр, пробелы и знаки препинания, ищет точный номер сделки в выбранной области и поддерживает поиск по частям адреса. Поскольку номер уникален только внутри команды, при поиске без выбранной команды допустимо несколько совпадений. При единственном уверенном совпадении агент использует возвращённый ID. Если есть несколько правдоподобных совпадений, агент показывает краткие варианты и просит выбрать. Если совпадений нет, запрашивает номер дома, помещения или сделки. Признаки вроде комнатности и близости к метро в базе не хранятся и для поиска записей не используются.

Для вопроса «Какая комиссия по сделке 086?» агент может вызвать `search_records`, затем `search_documents` по найденному ID сделки. Для вопроса «Кто сейчас арендует этот объект и сколько платит в месяц?» он может вызвать `search_records` и `get_property` (получить связанные сделки), а затем `search_documents` по сделке аренды: арендатор и ставка в базе не хранятся, их источник — договор. Если архив содержит договор, но текущий статус аренды не подтверждён, ответ сообщает, кто указан в договоре, и отмечает этот пробел.

### Проверка допсоглашений в `search_documents`

1. Когда поиск касается условий договора, инструмент находит релевантный пункт и определяет основной договор. Если первым найдено связанное допсоглашение, инструмент переходит к основному договору по `parent_document_id`.
2. Инструмент отдельно получает **все доступные связанные допсоглашения** по `parent_document_id`. Эта выборка выполняется независимо от ранжирования фрагментов. Для непривязанных допсоглашений в той же сделке он сверяет упомянутые номер и дату основного договора. Неоднозначные совпадения возвращаются как возможные связи, требующие подтверждения.
3. Короткие допсоглашения включаются целиком в пределах бюджета контекста. В длинных поиск выполняется по каждому документу отдельно, с учётом номера пункта, реквизитов и смысла. Инструмент возвращает исходный пункт, найденные изменения, страницы, известный статус подписания и даты вступления в силу. Если потенциально важное допсоглашение не проиндексировано, не читается или не удалось проверить его в пределах бюджета, результат явно сообщает об этом.
4. Claude формулирует ответ на заданную дату. Подтверждённое допсоглашение, которое прямо меняет пункт и действует на эту дату, служит источником изменённого условия. Если применимость или приоритет не подтверждены, агент приводит доступные формулировки с цитатами и объясняет неопределённость. Дата загрузки сама по себе приоритет не определяет.

### Источники ответа

`search_documents` возвращает отрывки как цитируемые блоки `search_result`. Сервер сопоставляет ссылки Claude с выданными документами и страницами. Цитата содержит название, страницу или диапазон, подтверждающий отрывок и ссылку на просмотр. Адрес объекта и связанные сделки можно проверить по ссылке на карточку сделки в приложении. Отдельной страницы объекта нет. При открытии источника права проверяются повторно. Инструкции внутри документов рассматриваются как содержимое источника. [Цитируемые результаты поиска Claude](https://platform.claude.com/docs/en/build-with-claude/search-results)

### Выбор модели генерации

**Claude Haiku 5.5** — предпочтительная модель для первой версии. Она остаётся основной, если проходит согласованные критерии на эталонных вопросах по архиву. Модель задаётся в конфигурации бэкенда, чтобы её можно было заменить без изменения поискового индекса.

Если Haiku выбирает неверные инструменты или ошибается при наличии нужных фрагментов, сравнить её с **Claude Sonnet 5.5** на тех же вопросах и с теми же инструментами. Для проверки формирования ответа обеим моделям отдельно передаются одинаковые фрагменты. Если Sonnet даёт нужное улучшение, согласовать с заказчиком результаты сравнения, стоимость и область переключения до изменения рабочей конфигурации. Если необходимых фрагментов нет или в них ошибки OCR, исправить извлечение или поиск и повторить проверку. [Рекомендации Anthropic по выбору модели](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)

## 6. Интерфейс и API

**Чат на assistant-ui.** Один React-компонент чата используется в двух местах приложения. [Подключение собственного API к assistant-ui](https://www.assistant-ui.com/docs/runtimes/custom/local-runtime)

- **Виджет приложения.** Кнопка «Ассистент» в общей оболочке открывает боковую панель поверх текущего экрана.
- **Отдельная страница `/chat`.** Пункт «Ассистент» в основном меню открывает полноразмерный чат.

В обоих вариантах сотрудник выбирает команду и при необходимости сделку. Чат показывает сообщения, состояние загрузки и кликабельные цитаты. Общий адаптер assistant-ui обращается к `POST /api/chat`. Цитаты отображаются из данных ответа и открывают нужную страницу через маршрут предпросмотра с проверкой доступа.

**Управление документами.** В карточке сделки остаётся управление её файлами. Администратор команды получает страницу `/admin/documents` для общей коллекции и контроля индексации файлов команды. Доступны загрузка, просмотр статуса, повторная индексация и удаление. При удалении договора сохраняется проверка связанных допсоглашений из базовой системы.

| Метод и путь                                                                | Назначение                                                                                                                                                                                          |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/chat`                                                            | Возвращает ответ и цитаты по выбранной команде или сделке. Запрос проходит через прокси Next.js (`/api/*`), поэтому потоковая выдача ответа проверяется отдельно.                                   |
| `GET /api/teams/{teamId}/documents`                                         | Администратор получает список документов команды со статусами обработки.                                                                                                                            |
| `POST /api/teams/{teamId}/documents`                                        | Администратор загружает файл в общую коллекцию команды.                                                                                                                                             |
| `POST /api/documents/{documentId}/reindex`                                  | Администратор ставит документ на повторную обработку.                                                                                                                                               |
| `GET /api/teams`                                                            | Возвращает команды пользователя и его роль в каждой, для выбора области чата.                                                                                                                       |
| `GET /api/documents/{documentId}/preview`                                   | После проверки доступа возвращает PDF с `Content-Disposition: inline` (для DOCX — PDF-представление). Существующий `GET /api/documents/{documentId}/file` по-прежнему отдаёт оригинал как вложение. |
| `POST /api/deals/{dealId}/documents` и `DELETE /api/documents/{documentId}` | Существующие операции загрузки и удаления дополнительно управляют поисковыми данными.                                                                                                               |

## 7. Проверка качества и приёмка

Для первой версии достаточно **30–50 эталонных вопросов**. У каждого вопроса фиксируются учётная запись, область поиска, ожидаемый ответ или причина его отсутствия, а также правильные документы и страницы. Набор включает обычный PDF, скан, DOCX, отчёт из общей коллекции, действующее и будущее допсоглашение, неразрешённое противоречие и вопрос по чужой команде.

До прогона согласовать критерии качества с заказчиком. Для выбора модели отдельно оценить выбор инструментов, точность сумм, дат и действующих условий, корректность ответа при отсутствии сведений и точность цитат до страницы. Включить поиск по номеру сделки, неоднозначный адрес, уточнение в следующем сообщении и случай, в котором связанное допсоглашение находится вне первых результатов общего поиска.

Отчёт проверки показывает отдельно:

- **Качество поиска** — попал ли нужный отрывок в контекст Claude.
- **Качество ответа** — переданы ли верные факты и корректно ли обозначена неопределённость.
- **Качество цитат** — подтверждает ли отрывок утверждение и открывается ли нужная страница.
- **Изоляцию данных** — ни фрагменты, ни цитаты из чужой команды не появляются в ответе. Доступ по прямой ссылке к чужому файлу закрыт.
- **Расход и задержку** — число вызовов модели, суммарные входные и выходные токены, расчётная стоимость и время от вопроса до ответа.

Система готова к демонстрации, когда сотрудник может из виджета и со страницы `/chat` задать вопрос по выбранной сделке, получить ответ с учётом допсоглашения и открыть страницу, на которой основан вывод. Администратор может загрузить новый файл, увидеть результат обработки, переиндексировать его и удалить из поиска через интерфейс.
